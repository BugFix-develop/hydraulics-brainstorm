# Регламент разработки и стандарты качества кода для ИИ-агентов (AGENTS.md)

> Данный файл размещается в корневом каталоге проекта и является обязательным сводом правил для всех взаимодействующих ИИ-агентов и разработчиков на кафедре АТП. Без этого файла в истории репозитория работа в агентном режиме считается оформленной некорректно.

---

## 1. Общие принципы разработки

0. **Анализ задания, проактивное предложение темы и запрет на преждевременные файлы:**
   * Завершив анализ загруженной лабораторной работы или методички, агент **ОБЯЗАН САМ предложить обсудить тему**, физические явления и математическую модель.
   * Агенту **строго запрещено создавать файлы проектной документации (`docs/*.md`), архитектуры или кода** до диалогового разбора модели с разработчиком, аудита задания на ошибки и получения явного подтверждения понимания модели.
   * Единственное разрешенное действие до согласования модели — создание файловой структуры (`mkdir -p docs include src tests`).
1. **Разработчик — менеджер контекста (Снижение когнитивного риска):**
   * Разработчик отвечает за когнитивные риски. **Категорически запрещено «вайбкодить» фундаментальные вещи**, в которых разработчик разбирается впервые.
   * Контекст оформляется в виде самодостаточного документа **«Описание бизнес-логики»** (`docs/<n>_<topic>.md`), который без «воды» и без привлечения иных источников объясняет решаемую задачу, уравнения и почему этих действий достаточно.
   * В документе бизнес-логики **запрещено** писать код C++, приводить классы и файлы.
2. **Обязательное наличие и аудит `AGENTS.md` в корне репозитория:**
   * При старте сессии агент обязан проверить наличие `AGENTS.md` в корне репозитория.
   * Если файл отсутствует — агент немедленно создает его из шаблона `templates/AGENTS.md`.
   * Если файл уже есть — агент прочитывает его и дополняет недостающими правилами, не затирая пользовательские настройки.
3. **Строгое переиспользование существующего кода (Code Reuse & Integration):**
   * **Категорически запрещено пересоздавать функции, структуры данных и классы, которые уже есть в проекте.**
   * Перед проектированием новой функциональности агент обязан проанализировать существующие файлы в `include/` и `src/` (из предыдущих лабораторных работ или модулей).
   * Все существующие типы данных (геометрия трубы, свойства среды, математические утилиты, базовые графы) переиспользуются напрямую через `#include`.
   * В архитектурном документе явно фиксируется список переиспользуемых сущностей в противовес новым.
4. **Обязательная пауза после создания файлов в `docs/` (Шлюз 1):**
   * После генерации Markdown-документов (`docs/<n>_<topic>.md`, `architecture.md`, `plan.md`) агент обязан **ПОЛНОСТЬЮ ОСТАНОВИТЬСЯ** для ознакомления разработчика с документацией.
   * Начинать реализацию кода в `include/` и `src/` разрешено **ТОЛЬКО** после явной команды пользователя: *«Документы утвердил, приступаем к реализации»*.
5. **Жесткое правило «Ровно один этап плана за один ответ» (One Stage Per Turn):**
   * Агенту **категорически запрещено объединять несколько этапов плана `plan.md` в одном ответе** (например, генерировать CMakeLists.txt, базовые структуры и класс-солвер в одной реплике).
   * В каждом отдельном ответе агент реализует файлы **ТОЛЬКО ОДНОГО** текущего этапа.
   * После генерации файлов текущего этапа агент **ОБЯЗАН НЕМЕДЛЕННО ОСТАНОВИТЬСЯ**, прекратить любые вызовы инструментов записи и редактирования файлов, отчитаться о сделанном и завершить сообщение.
   * Приступать к следующему этапу разрешено **ТОЛЬКО В СЛЕДУЮЩЕМ СООБЩЕНИИ** после команды: *«Этап проверил, переходим к следующему»*.
   * *Режим эксперта:* Если разработчик явно скомандовал *«режим эксперта»*, *«без остановок»* или *«/expert-mode»*, ограничение на 1 этап за ход снимается для вычислительного ядра (шлюз перед тестами и запрет на автокоммиты сохраняются всегда).
6. **Обязательная пауза перед написанием тестов (Шлюз 3):**
   * Перед созданием файлов GoogleTest в каталоге `tests/` агент обязан остановиться в чате, разобрать тест-сценарии по 4-уровневой пирамиде, согласовать независимые эталонные значения и дождаться подтверждения студента.
   * Категорически запрещены тесты-тавтологии (`EXPECT_EQ(calc(x), calc(x))`).
7. **Управление Git принадлежит исключительно человеку:**
   * ИИ-агенту запрещено автоматически коммитить (`git commit`) или пушить (`git push`) код без явного указания пользователя. Коммиты выполняет разработчик вручную после личного код-ревью.
8. **Категорическое разделение файлов по каталогам (File Separation Standard):**
   * Папка `include/`: исключительно заголовочные файлы (`.h`, `.hpp`).
   * Папка `src/`: исключительно файлы реализации (`.cpp`, `.c`).
   * Папка `tests/`: исходные файлы автотестов (`.cpp`).
   * Папка `docs/`: проектная документация (`.md`).
   * **Запрет смешивания:** Категорически запрещено держать `.h` и `.cpp` в одной папке. Header-only шаблоны и структуры располагаются в `include/` без создания `.cpp`.

## 2. Стандарты C++ и Code Style

1. **Стандарт языка:** C++20 (или C++17).
2. **Стиль именования:** строго `snake_case` для всех сущностей (функции, методы, переменные, структуры, классы, файлы).
3. **Суффикс структур и типов данных:** все структуры, псевдонимы типов (`using`) и классы обязаны иметь суффикс `_t`:
   * `pipe_properties_t`, `fluid_state_t`, `linear_nodal_solver_t`.
4. **Полнота и физический смысл имен:** запрет на непонятные однобуквенные сокращения (`density` вместо `rho`, `kinematic_viscosity` вместо `nu`, `flow_rate` вместо `q`).
5. **Константы:** физические и математические константы оформляются как `constexpr` (`standard_gravity = 9.80665;`, `atmospheric_pressure = 101325.0;`).
6. **Защита заголовков:** `#pragma once` в первой строке каждого заголовочного файла.
7. **Лаконичные Doxygen-комментарии (Strict Concise Documentation):**
   * Запрещены многословные «простыни» текста и комментарии, пересказывающие очевидный код.
   * Поля структур документируются строго в одну строку с единицами измерения в квадратных скобках:
     ```cpp
     double pipe_diameter{0.0}; ///< Внутренний диаметр трубопровода [м]
     ```
   * Методы классов снабжаются лаконичными блоками Doxygen:
     * `@brief` — краткое назначение в 1 строку;
     * `@param` — назначение аргумента и единицы в СИ в 1 строку;
     * `@return` — физический смысл возвращаемого значения в 1 строку;
     * `@throw` — условия генерации исключений (`std::invalid_argument`, `std::runtime_error`).

## 3. Регламент работы с линейной алгеброй и Eigen

1. **Категорический запрет на явное обращение матриц:**
   * Запрещено писать `A.inverse() * b`. Это вычислительно неэффективно и численно нестабильно.
2. **Однократный проход FullPivLU (Проверка ранга и решение):**
   * Анализ обратимости/ранга и решение СЛАУ выполняются в один проход через единый объект `Eigen::FullPivLU`:
     ```cpp
     Eigen::FullPivLU<Eigen::MatrixXd> lu(A_block);
     if (!lu.isInvertible()) {
         throw std::runtime_error("Сингулярная система: неполный ранг");
     }
     Eigen::VectorXd z = lu.solve(b_vec);
     ```
   * Повторная факторизация через `PartialPivLU` не требуется.
3. **Контроль нормированной невязки:**
   * После каждого численного решения СЛАУ вычисляется нормированная невязка:
     $$\frac{\Vert \mathcal{A} z - b \Vert_\infty}{\Vert \mathcal{A} \Vert_\infty \Vert z \Vert_\infty + \Vert b \Vert_\infty} < 10^{-12}$$

## 4. Архитектурные принципы и Task Pattern

1. **Разделение данных и вычислителей (Task Pattern):**
   * Входные данные хранятся в неизменяемых структурах свойств (`*_properties_t`);
   * Результаты возвращаются в структурах результатов (`*_result_t`);
   * Солверы не хранят накапливаемого изменяемого состояния (Stateless).
2. **Инкапсуляция и валидация инвариантов:**
   * Входные параметры валидируются в конструкторах;
   * Некорректные физические параметры ($d \le 0, \rho \le 0$) вызывают `std::invalid_argument`;
   * Несовместность математической системы вызывает `std::runtime_error`.
3. **Pass only what you need:**
   * На границе модуля не передавать типы соседнего слоя «на всякий случай».
