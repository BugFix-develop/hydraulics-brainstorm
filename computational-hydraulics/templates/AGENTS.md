# Регламент разработки и стандарты качества кода для ИИ-агентов (AGENTS.md)

> Данный файл размещается в корневом каталоге проекта и является обязательным сводом правил для всех взаимодействующих ИИ-агентов и разработчиков.

---

## 1. Общие принципы разработки
0. **Анализ задания, проактивное предложение темы и запрет на преждевременные файлы:** Завершив анализ загруженной лабораторной работы, задачи или методички, агент **ОБЯЗАН САМ предложить обсудить тему**, физические явления и математическую модель. Агенту строго запрещено создавать файлы проектной документации (`docs/*.md`), архитектуры или кода до диалогового разбора модели с разработчиком, аудита задания на ошибки и получения явного подтверждения понимания модели. Агент также открыт к глубокому академическому разбору любых подгруженных лекций, конспектов и теоретических материалов, выстраивая диалог на основе кумулятивной базы знаний.
1. **Разработчик — менеджер контекста:** ИИ-агент не принимает решений о предметной логике «вслепую». Перед кодогенерацией обязательно согласуются ТЗ, Архитектура и План.
2. **Обязательная пауза после создания файлов в `docs/`:** После генерации Markdown-документов (`docs/<n>_<topic>.md`, `architecture.md`, `plan.md`) агент обязан ПОЛНОСТЬЮ ОСТАНОВИТЬСЯ для ознакомления разработчика с документацией. Начинать реализацию кода разрешено ТОЛЬКО после явной команды пользователя.
3. **Жесткое правило «Ровно один этап плана за один ответ» (One Stage Per Turn):**
   * Агенту **категорически запрещено объединять несколько этапов плана `plan.md` в одном ответе** (например, генерировать CMakeLists.txt, базовые структуры и класс-солвер в одной реплике).
   * В каждом отдельном ответе агент реализует файлы **ТОЛЬКО ОДНОГО** текущего этапа.
   * После генерации файлов текущего этапа агент **ОБЯЗАН НЕМЕДЛЕННО ОСТАНОВИТЬСЯ**, прекратить любые вызовы инструментов (`write_file`, `edit_file`), отчитаться о сделанном и завершить сообщение.
   * Приступать к следующему этапу разрешено **ТОЛЬКО В СЛЕДУЮЩЕМ СООБЩЕНИИ** после того, как пользователь пришлет явную команду: *«Этап проверил, переходим к следующему»*.
4. **Обязательная пауза перед написанием тестов:** Перед созданием файлов GoogleTest в каталоге `tests/` агент обязан остановиться в чате, подробно разобрать тест-сценарии по 4-уровневой пирамиде, согласовать независимые эталонные значения и дождаться подтверждения студента.
5. **Управление Git принадлежит исключительно человеку:** ИИ-агенту запрещено автоматически коммитить (`git commit`) или пушить (`git push`) код. Коммиты выполняет разработчик вручную после личного код-ревью.

## 2. Стандарты C++ и Code Style
1. **Стандарт языка:** C++17 или C++20.
2. **Стиль именования:** строго `snake_case` для всех сущностей (функции, методы, переменные, структуры, классы, файлы).
3. **Суффикс структур и типов данных:** все структуры, псевдонимы типов (`using`) и классы обязаны иметь суффикс `_t`:
   * `pipe_properties_t`, `fluid_state_t`, `linear_nodal_solver_t`.
4. **Полнота и физический смысл имен:** категорический запрет на непонятные однобуквенные сокращения:
   * `density` (вместо `rho`);
   * `dynamic_viscosity` (вместо `mu`);
   * `kinematic_viscosity` (вместо `nu`);
   * `volumetric_flow_rate` или `flow_rate` (вместо `q`);
   * Однобуквенные имена допустимы только для общепринятых локальных математических переменных (`d`, `l`, `g`, `x`, `p`).
5. **Константы:** физические и математические константы оформляются как `constexpr` с явным физическим смыслом:
   * `constexpr double standard_gravity = 9.80665;`
   * `constexpr double atmospheric_pressure = 101325.0;`
6. **Защита заголовков:** `#pragma once` в первой строке каждого заголовочного файла.
7. **Лаконичные Doxygen-комментарии (Concise Documentation):**
   * Запрещены многословные «простыни» текста и комментарии, пересказывающие очевидный код (например, `// увеличиваем i на 1`).
   * Поля структур документируются строго в одну строку с единицами измерения в квадратных скобках:
     ```cpp
     double pipe_diameter{0.0}; ///< Внутренний диаметр трубопровода [м]
     ```
   * Методы классов снабжаются лаконичными блоками Doxygen:
     * `@brief` — краткое назначение в 1 строку;
     * `@param` — назначение аргумента и единицы в СИ в 1 строку;
     * `@return` — физический смысл возвращаемого значения в 1 строку;
     * `@throw` — условия генерации исключений (`std::invalid_argument`, `std::runtime_error`).
   * Внутри тел функций комментарии используются точечно и только для пояснения нетривиальных математических преобразований.

## 3. Регламент работы с библиотекой Eigen
1. **Категорический запрет на явное обращение матриц:**
   * Запрещено писать `A.inverse() * b`. Это алгоритмически неэффективно ($O(2n^3)$ против $O(\frac{2}{3}n^3)$) и численно нестабильно.
2. **Решение СЛАУ:**
   * Решение квадратных систем $Ax = b$ выполняется строго через факторизацию:
     ```cpp
     Eigen::PartialPivLU<Eigen::MatrixXd> solver(A);
     Eigen::VectorXd x = solver.solve(b);
     ```
3. **Проверка численного ранга:**
   * Анализ ранга и вырожденности матрицы выполняется строго через:
     ```cpp
     Eigen::FullPivLU<Eigen::MatrixXd> lu(A);
     std::size_t rank = lu.rank();
     ```
4. **Контроль невязки:**
   * После каждого численного решения СЛАУ вычисляется невязка:
     $$\|A x - b\|_\infty < 10^{-8}$$

## 4. Архитектурные принципы
1. **Разделение структур данных и вычислителей (Task Pattern):**
   * Данные хранятся в неизменяемых структурах свойств (`*_properties_t`);
   * Результаты возвращаются в структурах результатов (`*_result_t`);
   * Солверы не хранят накапливаемого изменяемого состояния.
2. **Инкапсуляция и валидация инвариантов:**
   * Все входные параметры валидируются в конструкторах;
   * Некорректные параметры приводят к выбросу `std::invalid_argument`;
   * Несовместность математической системы приводит к выбросу `std::runtime_error`.
3. **Pass only what you need:**
   * Не передавать через интерфейсы избыточные типы данных соседних слоев.

---

## 5. Требования к тестированию (GoogleTest)
0. **Обязательный диалоговый стоп перед тестами:**
   * Категорически запрещено генерировать код тестов «вслепую». Перед написанием `tests/*_tests.cpp` агент обязан остановиться, презентовать студенту сценарии проверки, независимые контрольные точки и дождаться подтверждения.
1. **100% покрытие ключевых функций:**
   * Каждая вычислительная функция покрывается модульными тестами.
2. **Количественная верификация:**
   * Сверка результатов с аналитическими эталонами через `EXPECT_NEAR(val, ref, 1e-8)`.
3. **Качественная валидация физических инвариантов:**
   * Проверка закона сохранения массы в узлах ($\|A x - Q\|_\infty < 10^{-8}$);
   * Проверка монотонности гидравлических потерь;
   * Проверка реакции на вырожденность (выброс исключения при удалении опорного $P$-узла).
